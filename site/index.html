Envisible

Encrypted environment variables that live in your Git repo — one private key per device, no backend, no plaintext .env.

curl -fsSL https://envisible.sh/install | sh

Why Envisible

Sharing secrets shouldn’t mean pasting them into Slack or committing a plaintext .env by accident.

Lives in Git

Secrets travel with your code in a single committed .envis file. Clone the repo, you have the encrypted environment.

No backend

No accounts, no secrets server, no SDK. Nothing to run, nothing to trust beyond your own keys and your Git host.

Per-device keys

Each device holds its own private key. Grant and revoke access per person without ever sharing a password.

Transparent injection

A one-time shell hook loads secrets when you enter a project directory. Your apps never know Envisible exists.

How it works

Envelope encryption, kept simple.

  1. 1

    One key encrypts everything

    A random data key K encrypts all your secrets once, using XSalsa20-Poly1305.

  2. 2

    K is sealed for each device

    That key is then sealed for every authorized public key with a Curve25519 sealed box. Only the matching private key can open it.

  3. 3

    Granting needs only a public key

    Adding a teammate re-seals K for their public key — the secrets themselves are never re-encrypted.

  4. 4

    Revoking rotates the key

    Removing someone generates a fresh key and re-seals it for everyone who remains, so they can’t read future state.

Honest threat model

What Envisible protects — and, just as importantly, what it does not.

Repository exposure

The committed .envis holds only ciphertext, public keys, and sealed keys. Having the whole repo and its history reveals no plaintext without an authorized private key.

Revocation is forward-only

Rotating the key protects future commits. Someone revoked today can still decrypt the historical revisions they already had access to.

Already-exposed credentials

Rotating K can’t make anyone forget a database password or API token they already saw. Rotate those with the provider.

Private-key theft & loss

A stolen private key can decrypt repos it’s still active in — revoke it to rotate. If no authorized key survives, the secrets are unrecoverable: there is no central backup.

Device & runtime

A fully compromised device exposes what it can read. Once injected, secrets live in your shell environment and are readable by processes you launch — a deliberate trade for transparent local dev.

Repository write access

The user list isn’t signed, so anyone who can push could alter it. Protect .envis with branch protection and reviews.

Quick start

From zero to a shared encrypted environment in a few commands.

  1. 1

    Initialize in your repo

    Run this at your project root. It creates .envis, generates your device key, and installs the shell hook.

    cd my-project
envis init
  2. 2

    Add your secrets

    Set them one at a time, or import an existing dotenv file.

    envis set DATABASE_URL
envis set STRIPE_KEY sk_live_123
# or bring an existing file:
envis import .env
  3. 3

    Commit and push

    The .envis file is safe to commit — it only contains ciphertext and public keys.

    git add .envis
git commit -m "Add encrypted environment"
git push
  4. 4

    A teammate joins

    They clone the repo, request access, and push. You grant them — no secrets are re-encrypted.

    # teammate
envis request            # then commit & push .envis

# you, after pulling
envis grant              # pick their request from the list
  5. 5

    Use secrets transparently

    Open a new terminal and enter the directory. The hook injects the secrets automatically — your tools just work.

    cd my-project
npm run dev     # DATABASE_URL, STRIPE_KEY, ... already set

Manual

Every command. Arguments in [brackets] are optional; running the interactive commands with no argument opens an arrow-key picker.

Secrets

envis init [--id ID] [--no-hook]

Initialize .envis in the current directory. Installs the shell hook unless --no-hook.

envis set [NAME [VALUE]]

Create or update a secret. With no args, pick an existing secret or create a new one; prompts for the value without echo.

envis delete NAME

Delete a secret (asks to confirm). With no NAME on a terminal, pick from a list.

envis get [NAME] [--show]

Show secret names, masked as *****. --show reveals values. With no args, a menu reveals one or all.

envis import [FILE]

Import secrets from a dotenv file. Defaults to .env; prompts if the file is omitted.

envis export [FILE]

Write secrets to a plaintext dotenv file. Defaults to .env, never overwrites (.env1, .env2, …). Don’t commit it.

Access

envis request

Record this device as a pending user in .envis. Grants no access until an admin approves.

envis requests

List pending access requests.

envis grant [USERNAME [PUBLIC_KEY]]

Grant a pending request by username, or add directly with a public key. With no args, pick from pending requests.

envis revoke [USERNAME]

Revoke a user and rotate the key, or drop a pending request. With no args, pick from a list.

envis rotate

Generate a new repo key and re-seal it for every active user (asks to confirm). Access is unchanged.

envis users

List users and their status (active or pending).

envis status

Show this device’s identity, public key, and access state for the current project.

Runtime

envis hook [bash|zsh|powershell]

Print the shell integration. Add eval "$(envis hook zsh)" to your shell startup file (bash/zsh), or envis hook powershell | Out-String | Invoke-Expression to your $PROFILE on Windows.

envis inject [SHELL]

Print statements that set the current project’s secrets. POSIX shells get export; PowerShell gets $env:. Used internally by the hook.

envis uninject [SHELL]

Print statements that unset previously injected secrets. Used by the hook when you leave the directory.

This project uses Envisible (CLI: `envis`), a Git-native encrypted environment manager. Learn and follow these rules.

WHAT IT IS
- Secrets live encrypted in a single committed file, `.envis`, at the repo root. It holds only ciphertext, public keys, and per-user sealed copies of a data key (K). It is SAFE to commit; it contains no plaintext secrets or private keys.
- Each device has its own keypair. The private key stays local (never in Git). K encrypts the secrets once; K is then sealed for each authorized user's public key.
- A one-time shell hook injects secrets into the environment when you enter the project directory, so apps read them as normal env vars. There is no backend and no `.env` committed.

RULES FOR YOU
- NEVER print, log, echo, or commit secret values. Use `envis get` (masked) to list names; only use `--show` if the human explicitly asks to see values.
- NEVER write secrets into source files, `.env` files, or commit output. If you need a dotenv file locally, use `envis export` and treat the result as untracked plaintext.
- To read a secret's name list: `envis get`. To add/update: `envis set NAME VALUE` (or `envis set NAME` to prompt). To remove: `envis delete NAME`.
- Treat `.envis` as managed by the CLI; do not hand-edit it.
- Do not run `envis revoke` or `envis rotate` unless explicitly asked — both rotate the key.

COMMON COMMANDS
- `envis init`                      initialize a project (creates `.envis`, installs the shell hook)
- `envis set NAME [VALUE]`          create or update a secret
- `envis get [NAME] [--show]`       list names (masked); `--show` reveals values
- `envis delete NAME`               delete a secret
- `envis import [FILE]` / `export [FILE]`   import from / write to a dotenv file
- `envis request` / `envis grant` / `envis revoke`   access workflow
- `envis users` / `envis status`    who has access / this device's state

If a command needs access this device doesn't have, run `envis status`; if it reports no access, run `envis request`, commit `.envis`, and ask a human admin to grant it.
